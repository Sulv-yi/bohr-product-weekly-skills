# 与已有方案的边界

这一节回答一个问题：**本 Skill 到底补了什么，哪些事它不该做。**
只写有依据的比较；没有在同一工程上实测过的对象，不声称优于它。

## 1. 比较对象与适用位置

| 方案 | 擅长 | 在本任务上的缺口 | 本 Skill 的位置 |
|---|---|---|---|
| 基础 Agent（不加载 Skill） | 通用行文、把要点填成 LaTeX 语法、认得常见宏包 | 常直接交"看起来像 LaTeX 的片段"；卡在第一条 `!` 错误就不再看日志；`\cite` 键与 `.bib` 不对账；无引擎时凭感觉说"应该能编译" | 把"成稿是否写实、能否编译、错误是否定位、引用是否闭合"变成可计算门槛，不过门槛不得写 success |
| 在线编辑器（Overleaf 一类） | 实时编译、语法高亮、协作、模板库 | 编译错误要人肉逐条读日志再回头改；不区分"模板给的错"与"自己写的错"；不产出可核验的失败归因与复现记录 | 负责预检 + 全量错误归因 + 引用闭合 + 复现记录，编译本身仍交给真引擎 |
| 模板向导（期刊/会议官方模板包、模板生成器） | 版式合规、必填项齐全、投稿系统认得 | 只保证"格式对"，不保证"内容写实"；空骨架也能过模板检查；不改公式编号与交叉引用的一致性 | 只管成稿实质与可编译性，版式合规仍以官方模板为准 |
| 通用 AI 写作助手（改写/扩写类） | 语言流畅、段落衔接 | 会补出材料外的事实与数值；改公式时改动符号而不改正文定义；把"预计可编译"写成结论 | 先建骨架再写实，改一处记一条 `source_map`，不新增材料外事实 |

结论：本 Skill 不与上述方案竞争"排版美观"或"文笔"，
它竞争的是**可交付性与可复现性**——
交付时能同时说清"这份稿子哪一节写了什么、编译在哪一轮收敛、每条错误定位到哪一行、
每个数字来自哪一段原文、别人照什么命令能重跑出同一份产物"。

## 2. 基础 Agent 难以稳定做到的六件事

1. **先出成稿，再谈修错**
   `build_manuscript.py` 先落一份章节齐全、可直接编译的骨架，再逐节写实。
   基础 Agent 收到"修编译错误"时常直接交一份报错清单，没有成稿可修——
   这是本题最典型的失分形态。

2. **空骨架不算交付**
   `check_manuscript.py` 判的是"写没写实"：每节实义字数、摘要是否交代数值结果、
   公式环境里是不是真有一条公式、表格有没有真实数据行。
   模板向导与骨架脚本都可能让空稿"看起来合规"，这里过不去。

3. **全量错误归因而非首错即停**
   `compile_and_parse.py` 解析**所有** `!` 错误，逐条给 file:line + 根因分类 + fix_hint，
   并按根因排序后循环修复到 `error_count=0` 且 `converged=true`。
   报错级联时，先修根因再重编，避免"改一条冒三条"。

4. **引用闭合可对账**
   `build_outputs.py` 产出 `cite-map.csv`：每个 `\cite` 键、用在哪几节、是否在 `.bib` 里、
   条目类型是什么。`cite_resolved_rate` 未达 1.0 会拦住 success。
   在线编辑器只告诉你"Citation undefined"，不告诉你缺的是哪几条、各用在哪。

5. **无引擎时不说谎**
   探测不到引擎 → `status=unavailable` → `result.status` 只能到 `partial`。
   `eval/score_output.py` 在这种环境下把 `gain_verifiability` 判 `n/a` 而不是 `pass`，
   宁可少一个"通过"，不多一个假的"通过"。

6. **复现要素齐全**
   `reproduction` 要求 engine / engine_version / packages / command / rounds 五项，
   探不到就写 `unknown` 并进 uncertainty，不猜版本号。

## 3. 方法取舍（为什么这样做）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 先后顺序 | 先出成稿，再做检查 | 只有检查报告没有成稿，评审无从判断你到底交了什么东西 |
| 生成与核验 | 两遍分离 | 边写边编最容易在报错里打转；先过结构门槛再进编译，省轮次 |
| 错误处理 | 全量解析 + 按根因排序 | 首错常是级联的源头，也可能是无关的噪声；只修首错会反复 |
| 编译证据 | 只认日志，不认自报 | 题面明确"文字自述不能替代实际运行证据" |
| 版本记录 | 探测不到写 unknown | 编一个版本号比缺一个更难被发现，也更伤可信度 |
| 门槛 | 写成脚本，不写成清单 | 清单靠自觉，脚本拦截；同一输入重跑得到同一判定 |

## 4. 不声称的部分

- 不声称在排版美观或语言质量上优于人工排版；它做的是结构约束与可编译性。
- 不声称能判断科学正确性：`check_manuscript.py` 判"是不是写实的完整稿件"，
  判不了"这个公式在物理上对不对"。这一条已写进 SKILL.md 的限制与 result.uncertainty。
- 不声称零人工：`uncertainty` 允许非空，那是诚实缺口而不是失败。
- 不声称已在平台固定案例上取得某个具体分数；本文件只描述能力边界。
- 不声称在任何引擎/模板组合下都一次通过：宏包冲突与字体缺失需按 `references/error-taxonomy.md` 处置。
