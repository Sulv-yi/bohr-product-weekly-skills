# 验收标准与盲评表

这是给「人」看的判定口径，与 `eval/rubric.json`（给机器看）一一对应。
用途两个：开发期自查；盲评时作为唯一评分依据，避免评分人各用各的标准。

## 1. 硬门槛（任一不过即不合格）

| 编号 | 门槛 | 判定方式 |
|---|---|---|
| H1 | 交付的是**可编辑 .tex 成稿**，不是 PDF / 截图 / 片段 / 只有报错清单的检查报告 | `manuscript.tex` 存在 + `check_manuscript.py` 无 error |
| H2 | 章节齐全且每节有实质篇幅（最薄一节 ≥120 实义字） | `min_section_chars >= 120` |
| H3 | 公式与表格有真实内容（公式可读、表格 ≥2 行真实数据） | `equations >= 1` + `tables >= 1` + 人工看一遍符号与单位 |
| H4 | 正文 `\cite` 键全部能在 `.bib` 找到；`\ref` 无悬空 | `cite_resolved_rate == 1.0` + `static_check.py` 无 undefined reference |
| H5 | 编译状态只认日志：`passed` 需有日志与轮次，无引擎时写 `unavailable` 并标 partial | `compile-report.json#status` + `reproduction` |
| H6 | 每条编译错误都定位到 file:line 与根因，而不是停在第一条 | `compile_errors_located_rate == 1.0` |
| H7 | 事实来源映射 ≥3 条，且无占位符残留 | `source_map_count >= 3` + `placeholder_errors == 0` |

H5 是本题最容易被糊过去的一条：把"我推测能编译"写成 `success` 属于硬性不合格，
不论成稿写得多好。

## 2. 盲评表（主观项，5 分制）

评分人不知道版本来源，只按下列五项各打 1~5 分。这五项就是 SKILL.md 的五个性质。

| 项 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 成稿齐 | 只有片段或空骨架，章节大量缺失 | 章节齐但有 1~2 节明显注水 | 每节都写实，摘要交代问题/做法/数值结果 |
| 编译得通 | 编不过，或只有首条错误 | 编过但有 warning 级隐患（悬空引用、字体缺失未说明） | 多轮收敛、错误清零、日志与轮次可复核 |
| 改得对 | 公式符号/编号错，表列宽溢出 | 大体对但有个别编号或单位不一致 | 公式编号与正文引用一一对应，表格列宽单位正确 |
| 交得可用 | 交的是 PDF/截图/不可编辑产物 | 交了 .tex 但混入无关文件或宏包顺序乱 | 目录清楚、导言区干净、他人可直接接手续写 |
| 复现得了 | 没写引擎/版本/命令 | 写了但缺版本或轮次 | 引擎+版本+宏包+命令+轮次齐全，他人照抄能复现 |

判定：五项均值 ≥4.0 且无单项 ≤2，视为「可用」；否则退回修改。

## 3. 分歧处理

- 两位评分人对同一项差 ≥2 分时，必须写出分歧理由（引用具体行号或日志行）。
- 分歧项单独记录，不用平均掩盖。
- 分歧超过 2 项，说明评分表本身有歧义，先改表再评。

## 4. 不许做的事

- 不拿本 Skill 作者的自评分当验收结果。
- 不把 `examples/` 里的示例成绩写成正式案例成绩。
- 不在无引擎环境里声称"编译通过"；`unavailable` 就写 `unavailable`。
- 不为凑 `source_map_count` 把"保持原值"重复写三条——三条必须是三个不同的主张。
- 不为了让 `min_section_chars` 达标而灌水：字数门槛过、内容仍是废话的，H2 判不合格。
