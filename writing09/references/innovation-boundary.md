# 与已有方案的边界

这一节回答一个问题：**本 Skill 到底补了什么，哪些事它不该做。**
只写有依据的比较；没有实测过的对象，不声称优于它。

## 1. 比较对象与适用位置

| 方案 | 擅长 | 在本任务上的缺口 | 本 Skill 的位置 |
|---|---|---|---|
| 基础 Agent（不加载 Skill） | 把要点写成通顺段落 | 六类要素常并成两三段；参数只报几个显眼的；数据集版本与划分含糊；对照不说是否同预算；限制写成"存在一定局限性" | 把六要素、参数表来源列、对照与复现要件、限制的失效场景变成可计算门槛 |
| 实验记录工具（W&B / MLflow 之类） | 记录曲线、超参、artifact | 记录是给人看的看板，不产出可投稿章节；不检查"正文里的数是否与配置一致" | 从记录里取要素，产出章节；一致性由正文-参数表对齐率把住 |
| 模板化 Methods 生成器 | 给固定小节骨架 | 填空式模板容易长出材料外数值；不追问缺口 | 骨架只保证结构，内容必须来自材料，且缺口要显式追问 |

结论：本 Skill 不与上述方案竞争"记录能力"或"文笔"，它竞争的是**可复做性与可追溯性**——
章节交付时能同时说清"这个数来自哪份配置、这个条件是否同预算、哪些信息材料里没有"。

## 2. 基础 Agent 难以稳定做到的四件事

1. **六要素各自成段**
   骨架脚本先落小节结构，`validate_result.py` 对缺件直接报错。
   基础 Agent 写方法章节时最容易把"参数"融进"设置"，导致参数表缺失。

2. **参数表带来源**
   要求每行标注 `config.yaml / train.log / 作者确认`，且带来源行占比 ≥80%。
   没有这一列，"这个 0.05 是权重衰减还是 dropout"就无从核起。

3. **正文与参数表不两张皮**
   `param_body_alignment` 检查表中取值是否在正文出现，
   避免"表里写 8，正文写 '较大的批大小'"这类漂移；反向的表外数值由对照人工抽查。

4. **对照与复现的要件化**
   对照六项（基线对象/版本/同预算/指标/统计/重复）与复现六项（版本/环境/种子/命令/数据/划分）
   逐项判定命中，缺哪项就报哪项，而不是笼统说"实验设置完整"。

## 3. 方法取舍（为什么这样做）

| 取舍 | 选择 | 理由 |
|---|---|---|
| 先后顺序 | 先抽要素表，再写正文 | 先写正文再回头找数，一定会补出材料里没有的值 |
| 数值处理 | 每个数值必须能在要素表找到来源 | 编造数值比留空更难被发现，也更伤复现 |
| 缺口 | 列成 questions_for_author，blocking 项不让标 success | 追问是交付的一部分，不是失败 |
| 限制 | 必须写出触发条件或阈值 | "存在一定局限性"对读者零信息 |
| 自评 | 用脚本算结构指标 | 文字自述不可复核 |

## 4. 不声称的部分

- 不声称能自动判断数值是否正确：脚本只查"来源标注齐不齐、正文与表对不对得上"，对错要对着配置文件逐条核。
- 不声称跨领域无需调整：六要素的名称与粒度需按领域替换（如临床研究需增加伦理与入排标准）。
- 不声称零人工：`open_gaps` 允许非零，那是诚实缺口。
- 不声称已在平台固定案例上取得某个具体分数。
